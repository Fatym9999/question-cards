# Этап 1. Supabase

Цель: отдельный проект, шесть защищённых таблиц и одна точка записи ответа.
К этапу 2 переходим после твоего «готово».

## 1. Создай отдельный проект

1. Открой <https://supabase.com/dashboard> и войди в аккаунт.
2. Нажми **New project** и выбери свою организацию.
3. В **Project name** введи `question-cards` — это название Supabase-проекта, не GitHub-репозитория.
4. В **Database password** сгенерируй пароль и сохрани его в менеджере паролей.
5. В **Region** выбери подходящий европейский регион, например Frankfurt, если он доступен.
6. Нажми **Create new project** и дождись завершения создания.

Не используй Supabase-проект от другого приложения: этот SQL предназначен для новой базы.

## 2. Выполни миграцию

Полный файл:
`/Users/roman/Documents/Codex/test/question-cards/supabase/migrations/20261116144615_initial_schema.sql`

1. В новом проекте слева открой **SQL Editor**.
2. Нажми **New query** (в некоторых версиях панели — **New Query**).
3. Оставь роль **postgres**, вставь содержимое файла целиком.
4. Нажми **Run** или `⌘ Enter`.
5. Ожидается успешное выполнение без ошибок: обычно **Success. No rows returned**.
6. В **Table Editor** в схеме `public` должны появиться:
   `decks`, `cards`, `review_logs`, `push_subscriptions`,
   `notification_settings`, `notification_schedule`.

Запускай миграцию один раз. Если после успешного запуска выполнить её повторно,
получишь `already exists`; это не причина удалять таблицы. При ошибке в первом запуске
транзакция откатывается. Если редактор оставил транзакцию в ошибочном состоянии,
сначала выполни отдельно `rollback;`, затем пришли текст ошибки.

На таблицах есть RLS. Для пяти пользовательских таблиц созданы SELECT/INSERT/UPDATE/DELETE
политики владельца. В дополнение к политикам права запрещают прямую запись полей
повторения и вставку/редактирование журнала из браузера. Их меняет только RPC.
У `notification_schedule` нет клиентских политик и нет клиентских прав;
доступ есть у серверной роли `service_role`.

Данные карточки и журнал сохраняются одним вызовом `record_review` и одной транзакцией.
Внутренняя функция проверяет владельца и блокирует строку на время обновления.
`p_expected_revision` должен совпадать с текущим `cards.revision`.
Повторный ответ со старой версией вернёт код `40001`; фронтенд обновит карточку,
не будет молча повторять оценку и не создаст второй журнал.

## 3. Проверь базу

1. **SQL Editor → New query**. Оставь роль **postgres**.
2. Вставь полный файл
   `/Users/roman/Documents/Codex/test/question-cards/supabase/tests/001_security_and_rpc.sql`.
3. Нажми **Run**. Ожидается результат:
   `OK: RLS, права, чужие колоды, RPC, версии и атомарный откат проверены`.
   Некоторые версии SQL Editor показывают только статус последней команды `ROLLBACK`;
   главное, чтобы не было ошибок `FAIL` или других ошибок SQL.
4. Скрипт временно создаёт двух тестовых пользователей, переключает роли и проверяет
   реальную изоляцию. В конце откатывает все тестовые данные. Не запускай его по частям.
5. В следующем запросе выполни полный файл
   `/Users/roman/Documents/Codex/test/question-cards/supabase/tests/002_inspect.sql`.

Ожидаемая таблица:

| table_name | rls_enabled | client_policies |
| --- | --- | --- |
| cards | true | 4 |
| decks | true | 4 |
| notification_schedule | true | 0 |
| notification_settings | true | 4 |
| push_subscriptions | true | 4 |
| review_logs | true | 4 |

SQL Editor под ролью `postgres` обходит RLS. Поэтому обычный SELECT в редакторе
не доказывает изоляцию; тест выше специально переключается в роли клиента.

## 4. Настрой вход по email и паролю

1. Открой **Authentication → Sign In / Providers**.
2. Включи **Allow new users to sign up**.
3. В списке провайдеров открой **Email**, проверь **Enable Email provider**.
4. Оставь **Confirm Email / Confirm email** включённым.
   В разных версиях панели переключатель находится в Email или в блоке User Signups
   на странице Sign In / Providers.
5. **Allow anonymous sign-ins** оставь выключенным.
6. Сохрани изменения кнопкой **Save / Save changes** в изменённом блоке.

Названия разделов сверены с документацией. Регистр букв и положение переключателя
могут различаться в версиях панели; если нужного пункта нет, пришли его название/текст экрана.

Встроенная почта Supabase подходит для первого теста на адресе участника команды
организации. По документации на 16.11.2026 она отправляет только на адреса команды,
с лимитом 2 письма в час на проект. Для проверки используй email своего аккаунта Supabase.
Открытая регистрация с подтверждением почты потребует **Custom SMTP** в Supabase Auth.
Это ограничение сервиса: для произвольных email одной встроенной отправки недостаточно.
Пока внешний почтовый сервис не подключаем. Отключать подтверждение почты ради обхода
этого ограничения не нужно.

Регистрацию из самого приложения проверим на этапе 2, когда появится форма входа.

## 5. Настрой адреса Auth

Имя GitHub-репозитория ещё не выбрано. Для первого локального запуска:

1. **Authentication → URL Configuration**.
2. В **Site URL** укажи `http://localhost:8000/` и нажми **Save**.
3. В **Redirect URLs** нажми **Add URL**, добавь `http://localhost:8000/` и сохрани.

Это временный адрес разработки. HTTP разрешён для localhost.
Пока не открывай ссылки подтверждения регистрации: самого приложения ещё нет.

На этапе 2, после выбора репозитория и `BASE_PATH`, заменим **Site URL** на
`https://fatym9999.github.io/ИМЯ-РЕПОЗИТОРИЯ/` и добавим такой же точный адрес
в **Redirect URLs**. Не вставляй `ИМЯ-РЕПОЗИТОРИЯ` буквально.
Для локального запуска с таким же base path добавим
`http://localhost:8000/ИМЯ-РЕПОЗИТОРИЯ/`.

Для обычного статичного приложения оставь стандартный шаблон подтверждения
со ссылкой `{{ .ConfirmationURL }}`. Серверный маршрут `/auth/confirm` создавать не нужно:
подтверждение выполняет Supabase, а возврат в приложение обработает браузерный клиент.

## 6. Сохрани публичные параметры подключения

1. В верхней части проекта нажми **Connect**: там можно получить **Project URL**
   и **Publishable key** для клиента.
2. Ключи также находятся в **Settings / Project Settings → API Keys**.
3. Нужен ключ вида `sb_publishable_...`, а не secret key.
4. Если ключей ещё нет, создай publishable key в **API Keys**.

На этапе 2 положим Project URL и publishable key в один файл конфигурации.
Публичный ключ можно хранить во фронтенде и репозитории: доступ ограничивают Auth и RLS.
Secret key `sb_secret_...`, legacy `service_role` и пароль базы во фронтенд не попадают.
Серверные ключи на этом этапе копировать и присылать не нужно.

Проверь также **Integrations → Data API → Settings**:
Data API должна быть включена, а схема `public` — входить в **Exposed schemas**.
`app_private` туда не добавляй. Если Data API в твоём интерфейсе находится
в **Project Settings → Data API**, открой этот раздел.
Миграция уже выдаёт явные права таблицам — полагаться на автоматические GRANT не нужно.

## 7. GitHub Pages

На этом этапе настройки хостинга не меняем: HTML-приложения ещё нет.
SQL выполняется в Supabase, а файлы миграции хранятся в репозитории для истории.
Когда выберем репозиторий на этапе 2, добавим файлы в `dev`; после проверки сделаем
слияние в `main` по твоему обычному процессу. Слияние веток само по себе не выполняет SQL в Supabase.

## При переезде на moonhaze.ru

1. Сохраняем тот же Supabase-проект: данные и пользователи остаются.
2. Меняем единственную константу `BASE_PATH` и адрес приложения для серверных push.
   Статический manifest и service worker должны получать тот же путь; способ зададим
   на этапе PWA без добавления сборки фронтенда.
3. В **Authentication → URL Configuration** меняем **Site URL** и **Redirect URLs**
   на новый HTTPS-адрес вместе с полным путём и завершающим `/`.
   На время переноса можно держать оба точных адреса, затем удалить старый.
4. Обновляем ссылку в payload push, разрешённый Origin серверных функций и адреса
   VAPID, если они зависят от домена. Детали будут в этапе 4.
5. Подписки push и установленное PWA на новом адресе создаём заново.
   Старый service worker и разрешения другого origin не переносятся.
6. В Nginx обеспечиваем HTTPS и выдачу файлов приложения по новому base path;
   scope service worker должен покрывать приложение.
